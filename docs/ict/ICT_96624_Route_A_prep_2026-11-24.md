# 96624 Route A ICT Demo — Status and Blocking Defects (2026-11-24 night)

Target: an ICT demo project for **96624 / A-96624 (S32N79 RDB)** built from the
customer's NET + SPF + BoM drop, using the Yaml Build page logic (Route A), so
the ICT stage can be rehearsed in Virtual and then on the rack.

generator resolves them relative to the repo):

## 1. What already exists

`scripts/build_96624_ict_demo_yaml.py` (≈340 lines, v1.0.1 logic) does the
whole Route A chain headlessly:

1. parse `NET-96624_A.net` → classify nets into Power / Clock / GPIO;
2. allocate against the rack pools — 80 DAQM908A sense points, 12 U2355A
   analogue inputs, 3 single-ended clock inputs (DAQM907A totalizer), 24 DIO;
3. write power and clock limits, group the rows into `standard_ict_sequence`
   (`Init Instruments` → `Fixture Ready` → R-GND → `DAQ AI Start` →
   `Power On DUT` → `DAQ AI End` → Power Voltage → Clock Hz → `Power Off DUT` →
   `Reset Instruments`);
4. write the YAML, reload it through `project_config.load_config`, then run the
   whole flow in Virtual and print the failures.

## 2. What it produced tonight

`projects/96624/A-96624_ICT_Demo_v1.0.1.yaml` — **34 ICT cases / 0 FCT cases /
12 rails**, channels: 82 power, 20 clock, 24 GPIO. Row order is correct and the
YAML reloads cleanly through the production loader.

Virtual result: `Overall Result: FAIL`, 12 rows:

| Rows | Test | Console reason |
|---|---|---|
| 17–24, 27 | `Power Voltage` | `DAQM: slot1 CH101: DCV = 0.001 V but PSU output is OFF (11.4..12.6 V expected) -> FAIL` |
| 29–31 | `Clock Hz` (EXTAL, SXOSC_EXTAL, SXOSC_XTAL) | `DAQM907A totalizer ...: 0 Hz (DUT unpowered) -> FAIL` |

So the 12 V rail rows, the 1.2 V / 1.8 V rows and the three clock rows all fail
for **one** reason: the DUT is never powered.

## 3. Root cause (open, with evidence)

`Power On DUT` is deliberately a passive state carrier — the N5747A setpoints
live in the Equipment Config block, never in the row
(`mtkgui/engine/steps.py:98-101`). The demo's `equipment` section, however,
carries the **display-only** N5747A panel (`psu.fields`: Model / Output /
Interfaces / Status) and nothing numeric:

```
equipment keys: [..., 'psu', 'psu_detail', 'fixture', ...]
psu: {"title": "N5747A DC Power Supply", "fields": {...}}
```

`equipment_config.py` knows how to emit the real setpoints
(`{"psu": {"voltage": config.psu_voltage, "current_limit": config.psu_current_limit}}`,
line 347) and the model exposes `set_equipment_config()` (`model.py:434`), but
the generator never calls it, and the produced file has neither `psu.voltage`
nor the rails capture block:

- `yaml_build.modules.rails` is empty (`on_voltage_v: None`, `sequence: []`);
- `test_workflow.power_rails_up_sequence` holds only the 12 rail names with
  duration — no setpoints.

Virtual then takes the `powered=False` branch of `measure_dcv`
(`mtkgui/virtual_hardware.py:380-413`), which is exactly the message above.

**Attempted fix, negative result:** inserting
`model.set_equipment_config(EquipmentConfig())` next to
`set_channel_allocation()` (i.e. 12.0 V / 3.0 A, the dataclass defaults) and
rebuilding changed **nothing** in the YAML — the `psu` block still held display
fields only. The change was reverted so the generator stays at its committed
state. This means the gap is not "the generator forgot a field"; the
`EquipmentConfig → YAML` write path itself is not carrying the setpoints for a
project built this way, and that is where the next probe must start
(`set_equipment_config` → `to_dict()` key → YAML emitter, plus whatever
`apply_to_window` does with it).

## 4. Second defect, found while reading the plan

Every clock row was written with `Expected = 32768.0 Hz / ±50 ppm`, including
`EXTAL` — a board-level main crystal, orders of magnitude faster than the
32.768 kHz RTC domain. Applying one limit to all clock nets is an inherited
simplification, not a measurement. Correct nominal values must come from the
SPF, per net.

## 5. Third observation (display, low priority)

On failing `Power Voltage` rows the table showed **Measured = 12.000 / 1.200 /
1.800 V** — the nominal placeholder — while the verdict log said `0.001 V`.
The table must show the number the verdict used.

## 6. Decisions needed before the demo can be called done

1. **Board input voltage and current limit** for the N5747A on 96624: is the
   fixture feeding 12 V at 3 A, or a lower rail? Taken from the SPF power
   section, not guessed.
2. **Per-net clock nominals** (EXTAL, SXOSC_EXTAL, SXOSC_XTAL, …): real
   frequencies and tolerances, from the SPF.
3. **Rail setpoint source** — should the generator derive `on_voltage_v` per
   rail from the net's power classification, or should the engineer fill it on
   the Equipment Config tab (which is the documented editing entry point)?
