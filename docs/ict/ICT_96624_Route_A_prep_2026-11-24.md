Target: an ICT demo project for **96624 / A-96624 (S32N79 RDB)** built from the
customer's NET + SPF + BoM drop, using the Yaml Build page logic (Route A), so
the ICT stage can be rehearsed in Virtual and then on the rack.

## 1. What already exists

## 3. Root cause (open, with evidence)

`Power On DUT` is deliberately a passive state carrier — the N5747A setpoints
live in the Equipment Config block, never in the row
(`mtkgui/engine/steps.py:98-101`). The demo's `equipment` section, however,
carries the **display-only** N5747A panel (`psu.fields`: Model / Output /
Interfaces / Status) and nothing numeric:

```
equipment keys: [..., 'psu', 'psu_detail', 'fixture', ...]
psu: {"title": "N5747A DC Power Supply", "fields": {...}}
```

Two different places look like they own the setpoint, and only one of them is
read at run time:

- `equipment_config.py:347` emits `{"psu": {"voltage": ..., "current_limit":
  ...}}` for the Yaml Build node-04 card (`set_equipment_config()`,
  `model.py:434`) — planning data;
- the gateway reads **`equipment.psu.params["Voltage set (V)"]` /
  `["Current limit (A)"]`** off the Equipment page config
  (`instrument` gateway `_psu_setpoints()`, `instruments.py:593-605`), and
  refuses to guess when a key is missing.

The demo had neither: its `psu` block carried only `title` + `fields`, so the
planning path had nothing to mirror and the runtime had nothing to read. It
also had no rails capture block:

- `yaml_build.modules.rails` is empty (`on_voltage_v: None`, `sequence: []`);
- `test_workflow.power_rails_up_sequence` holds only the 12 rail names with
  duration — no setpoints.

Virtual then takes the `powered=False` branch of `measure_dcv`
(`mtkgui/virtual_hardware.py:380-413`), which is exactly the message above.

**Fix, step 1 (done):** the demo now declares the setpoints on the Source
Panel, in `apply_to_window()`:

```python
psu = window.equipment_page.configs.setdefault("psu", {...})
psu["params"].update({"Voltage set (V)": 12.0, "Current limit (A)": 3.0})
```

The produced YAML now ends the `psu` block with

```yaml
params:
  Voltage set (V): 12.0
  Current limit (A): 3.0
```

which is exactly what the gateway's `_psu_setpoints()`
(`mtkgui/engine/instruments.py:593-605`) demands — it refused to default a
missing setpoint, so this was a real prerequisite, not cosmetics.

**Fix, step 2 (open) — the 12 rows are still red, and the cause is now the
Virtual harness, not the project.** The verdict text comes from
`virtual_hardware.py:738`, `powered = self.psu.output_on`. In Virtual *demo*
mode the instrument module is the scripted shim in `mtkgui/engine/demo.py`,
whose `N5747ADriver.output_on()` is a no-op (line 246) — it never touches the
`VirtualRack` PSU created at `demo.py:375`. So the power row "passes", the rack
never energises, and every downstream measurement is judged unpowered. On real
hardware the same row drives the actual N5747A, so this blocks **only** the
offline rehearsal, not a real run.

Next probe for whoever picks this up: give the scripted `N5747ADriver`
(`set_voltage` / `set_current` / `output_on` / `output_off`) a reference to
`env.rack.psu` and mirror the state, then re-run the generator and expect the
12 rows to turn `PASS`. Nothing else about the demo has been proven wrong —
the row order, the allocation, the sequence and the reload all check out.


## 4. Second defect, found while reading the plan

Every clock row was written with `Expected = 32768.0 Hz / ±50 ppm`, including
`EXTAL` — a board-level main crystal, orders of magnitude faster than the
32.768 kHz RTC domain. Applying one limit to all clock nets is an inherited
simplification, not a measurement. Correct nominal values must come from the
SPF, per net.

## 5. Third observation (display, low priority)

On failing `Power Voltage` rows the table showed **Measured = 12.000 / 1.200 /
1.800 V** — the nominal placeholder — while the verdict log said `0.001 V`.
The table must show the number the verdict used.

## 6. Decisions needed before the demo can be called done

1. **Board input voltage and current limit** for the N5747A on 96624: is the
   fixture feeding 12 V at 3 A, or a lower rail? Taken from the SPF power
   section, not guessed.
2. **Per-net clock nominals** (EXTAL, SXOSC_EXTAL, SXOSC_XTAL, …): real
   frequencies and tolerances, from the SPF.
3. **Rail setpoint source** — should the generator derive `on_voltage_v` per
   rail from the net's power classification, or should the engineer fill it on
   the Equipment Config tab (which is the documented editing entry point)?

## 9. Closure (2026-11-25, m121)

The 12 red rows are gone. Root cause of the second layer was not the demo but
the **virtual rack contract**: `VirtualRack.execute_op` still read a legacy
`params["voltage"]` key, while the M83 power rows carry only `state: on/off`
and take their setpoints from `equipment.psu.params`. Every Power On therefore
executed `PSU: OUTP OFF`, all power rows measured 0.001 V, and the clock rows
reported "DUT unpowered".

What changed (m121):

- `VirtualRack` honours `state` and reads the setpoints from a
  `psu_setpoints` attribute; a missing setpoint is an **Error** naming the
  equipment keys, never a fabricated 12 V.
- `TestWorkFlowPage` hands those setpoints to the rack on both run paths
  (`Run` and the smoke-test `run_demo`), taken from
  `equipment.psu.params`.
- `HeadlessEnv` does the same for `python -m mtkgui.engine.demo`.
- The three nets with no limit (`VBAT_SENSE`, `VCC_OSC_AUXCLKIN`,
  `VDD2_LP5X`) are disabled with a `comment` reason instead of reporting TBD;
  TBD fails the ICT stage, and an unjudgeable row must not block a run.

Verified: `scripts/build_96624_ict_demo_yaml.py` →
`[RUN] Overall Result: PASS`, `all 31 enabled ICT steps PASS (virtual)`.
The plan now ships as `examples/ict_96624/` with load tests.

Still open in this document and unchanged by m121: the 32768 Hz blanket on
the three clock rows (a limit-source question), Route B, Route C, and the
board-level 12 V / 3 A values that are still placeholders.
